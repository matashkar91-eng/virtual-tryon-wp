# Virtual Try-On Studio · اتاق پرو مجازی

افزونهٔ مستقل وردپرس با رابط فارسی و راست‌به‌چپ برای فروشگاه‌های ووکامرس. تنظیمات هر فروشگاه از پنل انجام می‌شود و برای تغییر متن، محصول، رنگ یا پرامپت نیازی به تغییر کد نیست. نسخهٔ فعلی **پایهٔ قابل توسعه و قابل نصب برای آزمایش** است. یک ویرایش زندهٔ دو تصویری در حساب فروشگاه آزمایشی موفق شده است؛ دسترسی، کیفیت و هزینه در مدل‌ها و حساب‌های دیگر باید جداگانه سنجیده شود.

## امکانات پیاده‌شده

- شورت‌کد `[virtual_tryon]`، انتخاب محصول، پیش‌نمایش عکس، رضایت پردازش، وضعیت ساخت، دانلود و لینک خصوصی پیگیری؛ طراحی واکنش‌گرا و فارسی.
- فهرست صریح محصولات مجاز ووکامرس؛ محصول پیش‌نویس یا مخفی از کاتالوگ حذف می‌شود. فهرست مستقل اختیاری نیز وجود دارد.
- پنل تغییر عنوان‌ها، راهنماها، دکمه‌ها، بنر، لوگو، رنگ‌ها، گروه محصول، الگوی پرامپت، مدل، کیفیت ویرایش تصویر، محدودیت درخواست و زمان نگهداری.
- پنل ۵۰ درخواست اخیر با تصویر محصول انتخابی، ورودی و خروجی خصوصی، وضعیت، خطای قابل فهم، علت فنی پاک‌سازی‌شده و تکرار دستی درخواست ناموفق (حداکثر سه تلاش).
- صف پایدار دیتابیس، قفل اتمی هر درخواست، بازیابی صف با WP-Cron و انقضای لینک‌ها. قطع ارتباط یا خطای نامشخص باعث ارسال خودکار مجدد هزینه‌دار نمی‌شود.
- مهمان با سقف ساعتی به‌ازای IP و سقف کل فروشگاه؛ امکان الزام ورود. مهمان پیش‌فرض ۵ درخواست و کل فروشگاه ۵۰ درخواست در ساعت.
- تصاویر شخصی خارج از ریشهٔ عمومی وب، بازکدگذاری عکس ورودی، حذف متادیتای عکس، بررسی نوع واقعی، حجم و ابعاد فایل؛ کلید API فقط سمت سرور.

## نصب و اولین آزمایش

پیش‌نیاز: WordPress 6.5+، PHP 8.1+، GD یا Imagick، ووکامرس برای اتصال محصولات، HTTPS در سایت واقعی، و فضای قابل نوشتن **خارج از webroot**.

1. اجرا کنید: `python3 scripts/build.py`. خروجی `dist/virtual-tryon-wp-0.1.7.zip` را از «افزونه‌ها ← افزودن ← بارگذاری» نصب و فعال کنید.
2. از منوی «پرو مجازی»، محصولات مجاز و تصاویر واضح آن‌ها را انتخاب کنید. فقط نام محصول کافی نیست؛ تصویر مرجع برای API ارسال می‌شود.
3. متن‌ها، رنگ‌ها، بنر، لوگو، محدودیت‌ها و پرامپت را مطابق فروشگاه تنظیم کنید. مقدار `{product}` نام محصول و `{category}` نوع محصول است.
4. برگه‌ای بسازید و `[virtual_tryon]` را در بلوک شورت‌کد قرار دهید. حالت را روی **آزمایشی** نگه دارید و با یک تصویر غیرحساس تست کنید.
5. پس از اجرای cron، نتیجه و درخواست را در پنل بررسی کنید. در حالت آزمایشی همان تصویر ورودی برمی‌گردد؛ هیچ تغییر واقعی لباس یا روسری انجام نمی‌شود.

### فضای خصوصی

مسیر پیش‌فرض یک پوشهٔ مخصوص سایت در کنار ریشهٔ نصب وردپرس است. اگر قابل نوشتن نیست، مسیر مطلق خارج از همهٔ ریشه‌های عمومی وب و CDN را در `wp-config.php` تعیین کنید، مثلاً:

```php
define('VTO_PRIVATE_DIR', '/home/account/private/virtual-tryon');
```

این پوشه نباید با alias وب‌سرور یا همگام‌سازی CDN قابل انتشار باشد. افزونه مسیرهای داخل `ABSPATH`، `WP_CONTENT_DIR` و `DOCUMENT_ROOT` را رد می‌کند؛ تنظیمات alias سرور را میزبان باید بررسی کند. صرف وجود `.htaccess` را حفاظت کافی فرض نمی‌کنیم. اگر محل امن فراهم نباشد، دریافت عکس متوقف می‌شود. عکس مشتری به کتابخانهٔ عمومی رسانهٔ وردپرس اضافه نمی‌شود.

### صف و اجرای زمان‌بندی‌شده

برای توسعه، WP-Cron پیش‌فرض کافی است و اجرای آن به ترافیک سایت وابسته است. **برای فروشگاه واقعی، cron سیستم هر دقیقه لازم است**؛ مثلاً با WP-CLI و کاربر همان سایت:

```sh
wp --path=/absolute/path/to/wordpress cron event run --due-now
```

فقط پس از تنظیم cron مستقل، `DISABLE_WP_CRON` را فعال کنید. اجرای درخواست به سرویس ممکن است تا حدود دو دقیقه طول بکشد؛ محدودیت اجرای PHP/میزبان باید مناسب باشد. صفحهٔ پیگیری فقط وضعیت را می‌خواند و فراخوانی AI جدید ایجاد نمی‌کند. درخواست متوقف‌شده بعد از ده دقیقه در اجرای بعدی نگهداری، ناموفق می‌شود. پیش از تکرار دستی، مصرف حساب سرویس را بررسی کنید.

لینک دقیقاً پس از زمان انقضا از دسترس خارج می‌شود؛ حذف فیزیکی تصاویر و سوابق در اجرای بعدی کار نگهداریِ ساعتی انجام می‌شود. سیاست نگهداری باید تأخیر احتمالی cron، نسخه‌های پشتیبان میزبان و نگهداری سرویس خارجی را هم توضیح دهد. غیرفعال‌سازی افزونه فایل‌ها را نگه می‌دارد و زمان‌بندی را متوقف می‌کند؛ حذف افزونه از وردپرس تصاویر و جداول محلی آن را پاک می‌کند. در WordPress Multisite، فعال‌سازی شبکه‌ای در این نسخه پشتیبانی نشده است؛ برای هر سایت جدا فعال کنید.

## AvalAI: وضعیت واقعی اتصال

آداپتر فعلی دو تصویر (شخص و محصول) را به مسیر OpenAI-compatible زیر ارسال می‌کند:

```text
POST https://api.avalai.ir/v1/images/edits
Authorization: Bearer <server-side key>
multipart: model, prompt, quality, n=1, size=1024x1024, image[], image[]
response: data[0].b64_json OR data[0].url
```

این قرارداد با مدل `gpt-image-2.5-flare` در حساب یک فروشگاه به خروجی موفق رسیده است؛ این موفقیت دسترسی همهٔ حساب‌ها، پایداری سرویس، کیفیت یا قیمت آینده را تضمین نمی‌کند. دسترسی مستندات رسمی AvalAI در محیط توسعه با محدودیت شبکه مواجه شد و کلید معتبری در دسترس نبود. ممکن است در حساب دیگری مسیر ویرایش یا دریافت دو عکس پشتیبانی نشود. لینک چت `https://chat.avalai.ir/chat` مستند API نیست. پیش از حالت واقعی باید مستندات رسمی و پشتیبانی مدل انتخابی بررسی و یک درخواست زندهٔ کنترل‌شده اجرا شود. از نسخهٔ ۰٫۱٫۴، پاسخ استانداردِ شامل `data[0].url` نیز با دریافت امن تصویر از نشانی HTTPS عمومی پشتیبانی می‌شود.

طبق [تعریف عمومی ویرایش تصویر در SDK رسمی OpenAI](https://github.com/openai/openai-python/blob/main/src/openai/types/image_edit_params.py)، قرارداد image edit برای مدل‌های پشتیبانی‌شده آرایهٔ تصاویر و گزینهٔ کیفیت را تعریف می‌کند. این منبع نام `gpt-image-2.5-flare`، قابلیت آن یا مسیریابی AvalAI را تأیید نمی‌کند؛ تنها شاهد این پروژه برای آن شناسه، اجرای موفق مشاهده‌شده در حساب همان فروشگاه است. تنظیمات ذخیره‌شدهٔ فروشگاه در ارتقا پاک نمی‌شوند و مدیر می‌تواند شناسهٔ مدل را از پنل تغییر دهد.

کلید را در پنل امن تنظیمات افزونه وارد کنید یا ترجیحاً در `wp-config.php` قرار دهید:

```php
define('VTO_AVALAI_KEY', 'YOUR_KEY_FROM_SECURE_SETTINGS');
```

کلید را در Git، مرورگر، پرامپت یا گزارش خطا قرار ندهید. کلید ذخیره‌شدهٔ پنل در دیتابیس وردپرس به شکل رمزنگاری‌نشده ولی غیرautoload نگهداری می‌شود؛ دسترسی دیتابیس و پشتیبان‌ها باید محدود باشد. کلید در صفحه بازنمایش داده نمی‌شود و مقدار خالی آن را حفظ می‌کند. دامنهٔ API باید از میزبان فروشگاه قابل دسترس باشد. سیاست شبکهٔ این محیط توسعه از دسترسی میزبان وردپرس شما جداست.

هر دسته از روسری، لباس، عینک و زیورآلات باید با مدل مناسب و عکس واقعی مستقل ارزیابی شود. موتور تولید تصویر ممکن است طرح پارچه یا چهره را تغییر دهد؛ پرامپت تضمین حفظ دقیق جزئیات یا اندازه نیست. این افزونه در نسخهٔ فعلی موتور هندسی اندازه‌گیری بدن یا پرو زندهٔ دوربین ندارد.

### کنترل کیفیت و هزینهٔ هر تصویر

نسخهٔ ۰٫۱٫۶ مقدار `quality` را صریح می‌فرستد. گزینهٔ پیش‌فرض **اقتصادی (`low`)** است؛ `medium`، `high` و انتخاب خودکار سرویس (`auto`) نیز در تنظیمات وجود دارند. کیفیت‌های بالاتر و حالت خودکار می‌توانند توکن خروجی و هزینهٔ بیشتری ایجاد کنند. افزونه قیمت را تعیین نمی‌کند و انتخاب `low` مبلغ مشخصی را تضمین نمی‌کند؛ قیمت مدل، نرخ تبدیل و سیاست صورتحساب AvalAI ممکن است تغییر کند.

از نسخهٔ ۰٫۱٫۷، دستور ثابت سرویس صریحاً می‌گوید محصول موجود در عکس شخص باید کاملاً با محصول مرجع جایگزین شود و باقی‌ماندن عکس اولیه نتیجهٔ معتبر نیست. برای روسری، روسری فعلی باید از سر، گردن و شانه‌ها حذف و طرح، رنگ، حاشیه و ظاهر پارچهٔ روسری انتخابی بازسازی شود. این دستور پیش از پرامپت قابل تنظیم فروشگاه ارسال می‌شود تا متن کوتاه یا مبهم مدیر آن را خنثی نکند.

پس از ارتقا، تنظیمات فروشگاه را باز کنید، «کیفیت ساخت تصویر» را روی اقتصادی نگه دارید و ذخیره کنید. سپس فقط یک درخواست تازه با عکس و محصول ثابت بسازید و هزینهٔ همان بازه را در «AvalAI ← مصارف ← نمایش ← هزینه» بررسی کنید. درخواست‌های ثبت‌شده از نسخهٔ ۰٫۱٫۶ به بعد کیفیت انتخاب‌شدهٔ خود را نگه می‌دارند و تلاش دوبارهٔ هرکدام از همان کیفیت استفاده می‌کند. برای مقایسهٔ تنظیم جدید باید درخواست تازه بسازید. قبل از عرضهٔ عمومی نیز سقف درخواست افزونه و اعلان موجودی حساب AvalAI را متناسب با بودجه تنظیم کنید.

### بررسی اتصال بدون ارسال عکس

از نسخهٔ ۰٫۱٫۳، پس از ذخیرهٔ کلید و مدل، مدیر می‌تواند در صفحهٔ تنظیمات «بررسی اتصال و دسترسی مدل» را بزند. این بررسی فقط یک `GET https://api.avalai.ir/v1/models` انجام می‌دهد؛ عکس و پرامپت ارسال نمی‌شود و درخواست تولید تصویر ایجاد نمی‌کند. نتیجه دسترسی شبکه، احراز هویت و وجود نام مدل در فهرست را نشان می‌دهد؛ موفقیت آن پشتیبانی ویرایش تصویر یا کیفیت پرو را ثابت نمی‌کند. بررسی روی تنظیمات ذخیره‌شده انجام می‌شود و بین اجراها حداقل ۱۵ ثانیه فاصله لازم است.

خطاهای جدید اتصال، کد عددی cURL، دستهٔ خطا و زمان سپری‌شده را بدون متن خام خطا یا کلید ثبت می‌کنند: ۲۸ یعنی پایان مهلت، ۵/۶ خطای نام دامنه، ۷ برقراری اتصال، و ۳۵/۵۱/۵۸/۶۰/۷۷ خطای TLS. کد ۵۶ خطای دریافت داده است و به‌تنهایی مشکل پراکسی را ثابت نمی‌کند. هیچ‌کدام موجب ارسال خودکار دوبارهٔ درخواست ساخت نمی‌شود. خطاهای قدیمی نسخه‌های قبل جزئیات ازدست‌رفته را بازیابی نمی‌کنند؛ برای عیب‌یابی ابتدا بررسی بدون عکس را اجرا کنید.

از نسخهٔ ۰٫۱٫۵، زمان انتظار ۱۱۰ثانیه‌ای فقط هنگام همان درخواست ساخت تصویر در لایهٔ HTTP وردپرس و cURL دوباره اعمال می‌شود و توقف «سرعت پایین» cURL برای آن درخواست غیرفعال است. این محافظ پیش و پس از یک درخواست نصب و حذف می‌شود و روی بررسی مدل، دریافت نتیجه یا اتصال افزونه‌های دیگر اثر ندارد. اگر میزبان یا سرویس بالادستی سقف مستقل داشته باشد، افزونه نمی‌تواند آن را دور بزند. پایان مهلت هنوز نتیجه و صورتحساب را نامشخص می‌گذارد و باعث ارسال خودکار درخواست دوم نمی‌شود.

اگر پیش از ارتقا برای همین خطای ۳۰ثانیه‌ای یک کد موقت در Code Snippets فعال کرده‌اید، ابتدا فعال‌بودن نسخهٔ ۰٫۱٫۵ را در فهرست افزونه‌ها تأیید کنید و سپس فقط همان Snippet موقت را غیرفعال کنید. درخواست‌های ناموفق قبلی با ارتقا دوباره فرستاده یا بازیابی نمی‌شوند؛ پیش از «ساخت دوباره» تاریخچهٔ AvalAI را بررسی کنید.

اگر صفحه هنوز بنر آزمایشی یا عنوان قدیمی را نشان می‌دهد، کش همان صفحهٔ پرو را در افزونهٔ کش پاک کنید. اجرای واقعی یا آزمایشی هر درخواست از تنظیمات ثبت‌شدهٔ همان درخواست در گزارش مدیر مشخص است؛ تغییر تنظیمات، درخواست قبلی را تغییر نمی‌دهد. پیش از تکرار درخواست ناموفق، مصرف حساب AvalAI را بررسی کنید.

### دریافت نتیجه و بازیابی بدون ساخت دوباره

نسخهٔ ۰٫۱٫۴ قالب استاندارد base64 و لینک تصویر را می‌پذیرد. لینک‌های خروجی فقط از HTTPS عمومی با محدودیت حجم، زمان و تغییرمسیر دریافت می‌شوند؛ کلید API و کوکی به میزبان تصویر ارسال نمی‌شوند. نشانی امضاشدهٔ تصویر پیش از دانلود، به‌صورت فایل خصوصی با مجوز ۰۶۰۰ خارج از webroot ثبت می‌شود. اگر دریافت قطع شد، مدیر می‌تواند از «دریافت دوبارهٔ نتیجه (بدون ساخت جدید)» استفاده کند. این عملیات فقط GET انجام می‌دهد، درخواست تولید جدید نمی‌فرستد و تا سه بار مستقل از تلاش ساخت مجاز است. لینک خارجی ممکن است زودتر از زمان نگهداری افزونه منقضی شود.

نشانی خارجی در خروجی REST، صفحهٔ مشتری یا گزارش خطا نمایش داده نمی‌شود. پس از ذخیرهٔ موفق تصویر محلی یا حذف/انقضای درخواست، فایل مرجع هم پاک می‌شود. درخواست دارای مرجع با دکمهٔ ساخت دوباره ارسال نمی‌شود تا مصرف تکراری رخ ندهد.

برای پاسخ ناشناخته فقط وضعیت HTTP، نوع محتوا، اندازه و ساختار مجاز JSON ثبت می‌شود؛ متن پاسخ، تصویر، کلید و لینک خصوصی وارد گزارش نمی‌شوند. پاسخ ۲۰۲ به‌خودی‌خود به معنی آماده‌بودن تصویر نیست و مسیر پیگیری سرویس حدس زده نمی‌شود. **پاسخ درخواست‌های قدیمی که قبلاً دور ریخته شده‌اند، با به‌روزرسانی بازیابی نمی‌شود**؛ وضعیت آن‌ها باید در تاریخچهٔ AvalAI بررسی شود.

## حریم خصوصی و انتشار تجاری

لینک پیگیری یک **کلید دسترسی** تصادفی ۲۵۶بیتی است؛ فقط هش آن در دیتابیس ذخیره می‌شود. دارندهٔ لینک تا انقضا می‌تواند خروجی را ببیند؛ آن را به اشتراک نگذارید. مسیرهای نتیجه دارای no-store، no-referrer و noindex هستند. در reverse proxy/CDN، صفحهٔ دارای `vto_job` و همهٔ مسیرهای `vto/v1` را از کش، analytics، ضبط session و ثبت query حساس مستثنا کنید. افزونه نمی‌تواند تنظیمات ردیابی سایر افزونه‌ها یا لاگ وب‌سرور را کنترل کند.

رضایت صریح قبل از ارسال گرفته می‌شود. عکس و محصول در حالت واقعی برای AvalAI ارسال می‌شوند؛ مدیر سایت باید سیاست حریم خصوصی، شرایط سرویس و مدت نگهداری ارائه‌دهنده را به مشتری توضیح دهد. مدیر مجاز تصاویر ورودی و خروجی را می‌بیند. حذف محلی عکس، نسخهٔ احتمالی سرویس بیرونی یا backup را حذف نمی‌کند.

محدودیت IP از `REMOTE_ADDR` استفاده می‌کند و به هدر دلخواه کاربر اعتماد نمی‌کند. برای reverse proxy قابل اعتماد می‌توان فیلتر سمت سرور `vto_rate_identity` را با IP تأییدشده تنظیم کرد. IP در جدول درخواست‌ها ذخیره نمی‌شود؛ بودجه‌ها با HMAC ساخته می‌شوند. محدودیت IP به‌تنهایی ضدربات کامل نیست؛ قبل از عرضهٔ عمومی هزینه‌دار روی هاست خودتان حفاظت ربات، سقف هزینهٔ حساب و تست بار را هم تنظیم کنید.

این نسخه شامل سیستم لایسنس/اشتراک، درگاه پرداخت اعتبار، پنل مرکزی فروشندگان، worker مستقل، یا تضمین ترافیک بالا نیست. عرضهٔ عمومی باید بعد از تأیید سرویس زنده، تست staging و سیاست دادهٔ فروشگاه انجام شود.

## توسعه و آزمون

برای آماده‌سازی محیط ابری توسعه، `bash scripts/setup-dev.sh` را اجرا کنید. این اسکریپت PHP محلی، وردپرس، ووکامرس و دیتابیس SQLite جدا را بیرون مخزن آماده می‌کند و روی دیتابیس یا تنظیمات موجود بازنویسی نمی‌کند. دستورهای اجرای وب‌سرور و آزمون HTTP در خروجی آن آمده‌اند. در محیط محلی، cron عادی عمداً خاموش است؛ هنگام آزمایش تعاملی، `wp-cron.php` را مرتب با PHP اجرا کنید. نصب تازه، اجرای مجدد اسکریپت و فعال‌سازی ZIP در وردپرس جدا آزمایش شده‌اند. آزمون‌های خودکار باید فقط روی دیتابیس توسعه اجرا شوند؛ راهنمای دقیق در [tests/README.md](tests/README.md) است.

کدها از هم جدا هستند تا تغییرات بعدی روی همین پایه انجام شوند:

| بخش | مسئولیت |
| --- | --- |
| `Settings` / `Admin` | تنظیمات، برندینگ، محصولات و گزارش مدیر |
| `Catalog` | فهرست مجاز ووکامرس و محصولات مستقل |
| `Storage` | اعتبارسنجی و نگهداری خصوصی تصاویر |
| `Jobs` | صف، بودجه، قفل، تکرار و نگهداری |
| `Provider` / `Provider_Result` | اتصال تولید/ویرایش، خواندن نتیجه و دریافت امن خروجی |
| `Rest` | ثبت درخواست، وضعیت و تحویل خصوصی |
| `Frontend` / `assets` | شورت‌کد، طراحی و تعامل مرورگر |

برای تغییر ظاهر یا متن، اول تنظیمات را تغییر دهید؛ برای سرویس جدید آداپتر Provider را توسعه دهید. منطق صف را با UI مخلوط نکنید. برای روش اجرای آزمون‌های WordPress و HTTP، فایل‌های `tests` را ببینید. پاسخ‌های API در آزمون آداپتر شبیه‌سازی شده‌اند؛ این آزمون‌ها موفقیت API واقعی را ثابت نمی‌کنند.
